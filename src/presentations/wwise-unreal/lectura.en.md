## Class 1 · Data, programs and servers

Before talking about Wwise, there are three things to understand about any computer: how it moves data, what a program is and what a server is. They seem far from audio, but they are the ground for understanding why a game loads SoundBanks, what a sound engine does and how the game talks to it.

**The library.** To work with a piece of data, that data has to reach your hands. Picture a library. The shelves hold everything: every subject, every book there is. But getting up to fetch one is slow. On the table there are a few closed books from the subjects you are using: reaching them is a matter of stretching an arm. And right in front of you are the open books of the subject you are studying at this moment: reading them is instant. The rule is simple: the closer the information is to your hands, the faster you get to it, but the less of it fits. The table will never have the room the shelves have, and only two or three open books fit in front of you.

**The computer.** The library is your computer. The shelves are the hard disk: all your data, programs and audio live there, but loading something from disk is the slowest thing the machine does. The table is RAM: much smaller than the disk, but what is in it arrives in a fraction of the time. The open books are the cache, a tiny memory right next to the processor holding exactly what is in use at this instant. And the people reading are the CPU, the processor, which can only work with what it has in front of it. Disk, RAM and cache are not three different things: they are three distances to the processor. When a program says "loading", it is almost always data going up from disk to RAM.

**Languages.** The CPU does not understand Spanish, English or Python: it only understands ones and zeros, electrical pulses where 1 is on and 0 is off. That is machine code, the only language the processor reads. One level up is assembly: direct instructions to the processor that a human can write but finds very hard to read. Higher up are C++ and Rust, languages that give full control of the hardware and memory and that are compiled, that is, translated to machine code before running. And at the top are Python and JavaScript, which read almost like English and where the language itself manages memory for you. You write at the highest level you can; the CPU always reads the lowest. The higher up, the easier for you; the lower down, the faster for the machine. That is why Unreal and Wwise are written in C++: a game needs speed.

**The restaurant.** A server is a program that handles requests. Think of a restaurant. You, sitting at the table, ask the waiter for a burger the way you like it. The order reaches the kitchen, and the kitchen does three things: it checks that the dish is on the menu, it checks and brings the ingredients, and it cooks the burger. Then the waiter brings it to you, or brings you the news that there are no burgers. Receive an order, check that it can be fulfilled, prepare it and return it: that, and only that, is what a server does.

**Client and server.** Now change the names and you have computing. You are the client: the computer that asks. The kitchen is the server: the computer that answers. What you send is a request, carrying what you want and how you want it. What comes back is a response, or an error if it could not be done. And the kitchen's three steps are the same: the server validates the user (who are you, are you allowed?), fetches the resources it needs and builds the response before sending it. Every time you open a page, watch a video or join an online game, you are the client of some server.

**Each server serves its own thing.** That is why it is called a server: because it serves, and always whoever asks. Each kind serves one thing. A web server serves pages: you ask for a page and it returns it (Apache and Nginx are the most used). An FTP server serves files: you ask for one and it sends it (FileZilla Server, vsftpd). A database server serves data: you ask for some records and it returns them (PostgreSQL, MySQL). The pattern is always the same; what changes is what is asked for and what is delivered.

**The machine.** A server computer has the same parts as yours, CPU, RAM and disk, but with opposite priorities, because it is built to serve all day. Its network cards are extremely fast and robust, because that is where requests come in and responses go out, day and night. Its power supply is very robust, because it is on 24/7. And its video card does not exist: nobody looks at its screen. Compare it with a graphic design PC: a basic network card, a basic power supply and a powerful video card, because there all the work shows on screen. Same parts, different use: hardware is chosen by what the machine is going to do.

**Startup.** Let us put it all together with a game on a phone. The game is installed on disk with its SoundBanks: soundbank_init, soundbank_menus and soundbank_nivel_1. At startup only the minimum goes up to RAM: the game engine, the main scene, the sound engine and soundbank_init. The rest waits on disk. When the main scene tells the sound engine "play the menu", the sound engine does not have that music yet, so it goes to fetch soundbank_menus from disk and loads it into a free spot in RAM. Only then can it play. And soundbank_nivel_1 stays on disk, because nobody has asked for it. That is how a game keeps memory small: banks go up when they are needed, not before.

## Class 2 · What is an audio engine?

Wwise is described as an "audio engine" and Unreal as a "game engine". This class explains what the word engine means, starting from how programs run.

**Compiled and interpreted.** There are two ways for a program to get to run. A compiled program is written as text and translated once, before running, by a compiler; the result is a binary (game.exe, for example): ones and zeros ready for the CPU. An interpreted program is not translated: when it runs, it is still text. That leaves a question open, and it is the question of this class: if the CPU only understands binary, who reads that text?

**Compiled programs are run by the OS.** A compiled program is run by the operating system. The binary already speaks the machine's language, so Windows, macOS or Linux only have to launch it: they reserve memory for it and hand it control. From then on it is direct instructions to the CPU, which executes the binary as is. Nobody translates it at runtime, and that is why compiled programs are fast.

**Interpreted programs are run by an engine.** An interpreted program is run by an engine. The stack gains a floor: your script runs on the engine, the engine runs on the OS, and the OS on the CPU. The engine is an interpreter: just another program, compiled like any other, whose job is to read your text live and do what it says. The CPU never sees your script; it sees the engine reading it. Python is an engine for .py scripts; the browser is an engine for HTML and JavaScript.

**What an engine is.** From there comes the definition: an engine is a program that runs in order to run programs. It takes programs made of resources, code and configurations (sometimes programmed, sometimes only configured) and produces behaviour. The browser runs HTML and JS. Python runs scripts. Unreal and Godot run scenes and scripts. Wwise runs Wwise objects. They are all the same idea at different scales: a program that is already running and brings to life whatever you hand it.

**Game engines.** A game engine runs configurations and code. The resources, textures, 3D models and audio, come from outside, made in other tools. The configurations are the scenes, maps and prefabs: decisions you make in the editor without writing code. The code is the gameplay scripts. Configurations and code use the resources, and the engine runs everything together: the result is the game. When you work in Unreal, almost all your work is configuring and programming; running it is the engine's job.

**Audio engines.** An audio engine follows exactly the same pattern, reduced to sound. The resources are songs, sounds and voices. The configurations are interactive sound configurations: tracks, buses, events, everything that decides when and how each thing plays. And the sound engine runs them and produces the audio. That is what Wwise is: an editor where you configure interactive sound, and an engine that runs those configurations inside the game.

## Class 3 · Wwise from the inside

With the definition of engine in hand, this short class places Wwise inside the pattern and walks the full path from the editor to the running game.

**Recap.** Wwise follows the pattern of every engine: resources outside, configurations, and an engine that runs them. Its resources are songs, sounds and voices. Its configurations are called Wwise objects: segments, containers, events and everything we will see in the objects class. Those objects, together with the audio, are packaged into SoundBanks, and the Wwise sound engine runs the SoundBanks to produce audio inside the game.

**End to end.** The full path goes through three places. The first is the Wwise editor: audio clips come in there and there the designer configures the Wwise Objects inside the Wwise project; when the project is ready, the editor generates SoundBanks, .bnk files that hold the structure and the media. The second is the engine editor, Unreal: the game project receives those SoundBanks, and a Wwise plugin exposes the API so your audio code can make Wwise calls, such as posting an event or setting a parameter. The third is the build, the game that ships: your code makes the Wwise calls, the Wwise engine receives them and, with the SoundBanks loaded in memory, produces the audio. The important part is this: the game never touches the objects. It only uses the interface, the calls. Everything that plays was decided in Wwise.

## Class 4 · The Wwise editor

Wwise has two halves: the engine that runs inside the game, and the editor where everything is configured. This class walks through the editor: what it is made of and how the screen is arranged for each task.

**Views.** The Wwise editor is not a fixed screen: it is assembled from views, panels that each show one part of the project. All of them open from the Views menu. There you find three families with submenus, Editors, Profiler and Utilities, and below them the direct views, one click away: Audio Device Meter, Audio File Importer, Loudness Meter, Meter, Project Explorer, Soundcaster and Transport Control. If you cannot find a panel, it is not lost: it is in that menu.

**The everyday ones.** Of all the views, three you will use in every session. The Project Explorer is for moving around: it shows the whole project hierarchy in tabs (Audio, Events, SoundBanks, Game Syncs…) and from there you select any object. The Transport Control plays the selection: whatever you have selected in the explorer plays when you press play. The Soundcaster is for testing and mixing: you drag in several objects and events, fire them in any combination and change switches and parameters live, as if you were the game.

**One editor per property.** Inside the Editors family there are editors that work on any Wwise Object, whatever its type. The main one is the Property Editor, with its General, Routing, Conversion, Positioning and Advanced tabs: that is where every object's basic properties live (volume, pitch, output bus, positioning…). But each big property has its own separate editor: the RTPC Editor for Game Parameter curves, the States Editor for per-state adjustments, the Effects Editor for the object's effects, the Stingers Editor for hits over the music, and the Metadata Editor for the object's extra data.

**One editor per object type.** Specialized objects also bring their own tailored editor: the Music Playlist Editor and Music Segment Editor for the music system, the State Editor and Switch Editor for game syncs, the SoundBank Editor for building banks, the Effects Editor for effect ShareSets, and the Event Editor for an event's actions. When you open one of those objects, Wwise offers you its editor.

**Layouts.** Since views are loose panels, there has to be a way to arrange them. A layout is exactly that: an arrangement of views on the screen. Two layouts can have the same views available and look completely different, because each task wants its own screen: designing does not need the same as profiling, and profiling does not need the same as mixing.

**The built-in ones.** Wwise ships one layout per task, each with its key. Designer (F5) is the daily one: creating and configuring Wwise Objects and Events. Profiler (F6) connects to the game and shows live what is playing and what it costs. SoundBank (F7) is for building and generating the SoundBanks. Mixer (F8) is for mixing as a whole: levels, buses and mixing sessions. Schematic (F9) shows the project structure as a diagram, with its routing. Audio Object Profiler (F10) profiles object-based audio. Voice Profiler (F11) follows every voice that plays: where it came from and how it got there. Game Object Profiler (F12) shows the registered game objects and their parameters live. And you can save up to four arrangements of your own as User Layouts (keys 1 to 4).

**Designer.** The Designer layout is where almost everything happens. On the left are the Project Explorer to navigate the hierarchy, the Contextual Help, which explains whatever you are pointing at, and the Transport Control to listen. In the centre there is a row of tabs with every open element (for example Main Audio Bus, Music Bus, Level One Segment), and below it the tabs of views that depend on the selected element: Selected Element Editor, RTPC, States, Effects, Metadata. On the right, the Property Editor with the object's properties. The idea is to navigate, edit and listen without switching screens.

## Class 5 · Wwise Objects

Everything configured in Wwise is a Wwise Object. This class presents the catalog, ordered by the path a sound follows from the moment the game asks for it until it leaves the speaker.

**The path of a sound.** Every sound in Wwise follows the same path, and to understand it we sort the objects into five families. The game, outside, only touches the first one: the Game Input, where it posts Events and sets Game Syncs. From there the Content objects fire, which is where the signal is born. The signal goes down into Mixing, the busses, and out through the device. Processing, the effects, acts on Content and on Mixing, and its parameters also come from the game. And everything inside, input, content, mixing and processing, travels packaged in SoundBanks, which is what the game loads. The game and the output stay outside.

**Five families, five questions.** This classification is not Wwise's: it is ours, to understand the path. Each family answers a question. Game Input: what does the game say? Those are the Events and Game Syncs. Content: what plays and how is it chosen? It splits into Sound and Structure, and each has its version for SFX (Sound SFX and Sound Voice; Random, Sequence, Switch and Blend) and for music (Music Track and Music Segment; Music Switch and Music Playlist). Mixing and Routing: where does the signal go? Those are the busses. Processing: what happens to the signal? Those are the effects and ShareSets. Packaging: how is it delivered? Those are the SoundBanks.

**Sound.** Of all the objects in Wwise, only five point at real audio. The Sound SFX is the workhorse: it has one or more audio sources. The Sound Voice is the same, but with one source per language, meant for dialogue. The Music Track is the audio of the music system, with sub-tracks and clips. The Music Segment is a timeline with tracks, cues, tempo and meter. And plug-in sources are generated sources, with no file: the Wwise Synth or a tone generator. Everything else in Wwise exists to decide whether, when, which and how these five play.

**Structure.** Containers produce no audio: they have children and a rule that decides how those children play. The Property Container has no rule: it only groups and passes properties down. The Random Container answers "which one?": it picks one of its children, with weights and without repeating. The Sequence Container answers "in what order?": it plays them one after another. The Switch Container answers "according to what the game says?": it picks by a Switch or a State. The Blend Container answers "how much of each?": it plays several at once and mixes them by RTPC. In music, the Music Playlist chains segments in order or at random, and the Music Switch picks segments according to the game, with transitions. Folders only organize.

**Inheritance.** In the hierarchy, what the parent has goes down to the children, but in two different ways. Relative properties, like volume and pitch, add up floor by floor: if footsteps is at −6 dB, player at 0 dB and footstep_grass at −2 dB, that sound comes out at −8 dB; footstep_metal, with −4 dB on enemy and −4 dB of its own, comes out at −14 dB. Absolute properties, like the output bus or the effects, are inherited as they are, unless a child overrides them: footstep_metal can override and go out through a Metal bus while its siblings keep going out through SFX. The practice is to configure on the parent what they share and touch on the child only the exception.

**Mixing and routing.** The Audio tab has three folders. Containers holds the content objects, and each one points at exactly one output bus. Busses holds the mix: the Main Audio Bus is the main output, and under it hang busses like SFX and Music; there are also Aux Busses, which are the destination of sends; the Master Motion Bus, which is not audible but vibration and haptics; and Secondary Busses, which send audio to other hardware. Devices defines where each main bus comes out: the Main Audio Bus to a speaker, the Motion Bus to the controller, a Secondary Bus to headphones. The rule is that the signal moves from the object to the bus: it is not copied.

**Aux busses.** The send is the exception: it is a copy. A Sound SFX sends its dry signal to its output bus, a single destination, and can also send a copy to an Aux Bus, Reverb for example, with a send level of its own for each object. The Aux Bus processes the copy and both end up in the Main Audio Bus: dry plus wet. A normal bus is one destination with no duplication; an aux bus is duplication for shared effects, like the reverb of a room that many sounds use at once.

**Effects.** An effect can go on the object or on the bus, and the difference is cost. On the object, every voice has its own instance: three voices, three reverbs, before mixing. It is flexible, but each instance costs CPU. On the bus, the voices come in, get summed, and a single instance processes the mix: three voices, one reverb. That is why reverb lives on an aux bus: one instance serves every sound that uses it.

**ShareSets.** A ShareSet is a central definition that is edited once and used everywhere. An Effect ShareSet Reverb_Hall can be used by a sound, a music bus and an aux bus, and changing one parameter changes all of them. There are ShareSets for Effects, for Attenuation (distance curves), for Conversion Settings and for Modulators (LFO, Envelope, Time). When one specific case needs its own version, you use Custom: a local copy that applies only there.

**Events.** The game only sees the Event. From code it is posted by name, Play_Footstep for example, and inside the event are the Actions: Play on the footsteps container, Set Switch surface to grass, Set RTPC car_rpm to 4200. The game never sees those actions, so changing what an event does, another sound, another switch, does not touch the code. One important limitation: Events take no arguments. You cannot post Play_Footstep "with 6000"; if another value is needed, another Event is needed. For variable values there are Game Syncs.

**Game Syncs.** Game Syncs are values that the game code sets and that objects, containers and busses read. There are four. The Switch is discrete and local: one selector per Game Object, so Enemy A walks on wood while Enemy B walks on tile. The State is discrete and global: one situation for the whole game, like Low Health, with transitions. The RTPC is continuous: a curve that turns a game value into a property, like the car's RPM into pitch. The Trigger is momentary: a single signal that lands on the next beat of the bar, for music stingers. Events say when; Game Syncs say how. Switch is which sound for this object; State is the situation for everyone.

**Packaging.** In the end everything has to be packaged and organized. SoundBanks hold Events, structures and media, and are what the game loads at runtime; Wwise can also generate Auto-Defined SoundBanks, one per Event. Work Units are .wwu files that split the project into pieces so a team can work in parallel with version control. Queries, for searching the project, and Sessions, for profiling and mixing, are editor tools, not runtime objects. Only the SoundBanks travel with the game; the rest stays in the editor.

**Closing.** The path of a sound, complete: the game touches the Game Input; the signal is born in Content, goes down into Mixing and out through the device; Processing acts along the path; and SoundBanks package it all so the game can load it. If you can place each object on that path, you know what it is for.
